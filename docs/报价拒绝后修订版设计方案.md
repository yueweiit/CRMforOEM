# 报价被客户拒绝后的修订版设计方案

版本：v1.1
日期：2026-08-06
状态：已实现
适用范围：客户已拒绝报价后的重新议价、重新审批、重新发送和版本追溯

## 1. 背景与问题

报价被客户拒绝后，业务员通常需要根据客户反馈调整价格、数量、MOQ、规格、成本构成或有效期，再次发起内部审批并发送给客户。

这一过程需要同时满足两个目标：

1. 操作员不必重新填写整张报价单。
2. 客户已经收到并拒绝的旧报价必须保持可追溯，不能被后续修改覆盖。

当前可考虑的处理方式有三种：

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 直接修改被拒绝的报价并恢复草稿 | 操作最少 | 会改变客户曾收到的业务凭证；旧审批结果可能错误地覆盖新价格 | 不采用 |
| 将被拒绝报价作废并手工重建 | 旧报价不再修改 | `客户拒绝`与`作废`语义混淆；重复录入且容易遗漏字段 | 不采用 |
| 普通复制为一张新报价 | 保留旧记录并减少录入 | 新旧报价缺少结构化关系，容易形成无法追踪的重复记录 | 不直接采用 |

本方案采用第四种方式：**创建报价修订版**。它使用复制提升操作效率，但由报价域建立明确的版本关系、状态重置和审计记录，不等同于通用复制。

## 2. 当前系统事实与设计冲突

当前系统已经具备报价业务状态、审批状态、报价历史快照和客户拒绝命令，但“客户拒绝后的编辑语义”尚未统一：

- `docs/OEM商业报价与样品全流程系统设计实现方案.md` 将 `CUSTOMER_REJECTED` 定义为客户拒绝后的终态。
- `apps/api/src/modules/commercial/commercial.service.ts` 当前只禁止编辑 `VOIDED` 报价，因此 `CUSTOMER_REJECTED` 仍可通过通用更新接口修改。
- 当前更新逻辑不会重置业务状态和审批状态，可能出现“报价内容已改变，但仍是 `CUSTOMER_REJECTED + APPROVED`”的审批失真。
- `apps/web/src/features/customers/detail/panels/QuotePanel.tsx` 当前同样只禁止编辑 `VOIDED` 报价。
- `QuoteHistory` 已保存修改前后快照，可以辅助追溯，但历史快照不能替代不可变的、可被邮件和下游业务引用的报价版本。

因此，实施本方案前需要将“客户拒绝是当前报价版本的终态”确立为报价域唯一合同，并删除与该合同冲突的直接编辑路径。

## 3. 设计决策

### 3.1 核心决策

1. `CUSTOMER_REJECTED` 是单个报价版本的终态。
2. 被客户拒绝的报价保持原状态和原内容，不自动作废，也不恢复为草稿。
3. 后续重新议价必须通过专用命令“创建修订版”。
4. 修订版是新的 `Quote` 记录，拥有新的主键、报价版本号、审批周期和发送周期。
5. 修订版与来源报价必须通过结构化字段关联，不能仅靠备注或单号文本推断。
6. 修订版初始业务状态为 `DRAFT`，审批状态为 `DRAFT`，必须重新提交审批。
7. 原报价与所有修订版共同组成一个报价版本链，详情页能够按时间顺序查看。

### 3.2 业务语义

`客户拒绝`表示客户真实拒绝了一份已经审批并发送的报价，它不是错误数据，也不是无效数据。因此：

- 原报价不转换为 `VOIDED`。
- 创建修订版后，原报价仍保持 `CUSTOMER_REJECTED`。
- “作废”仅用于录入错误、重复单据、主动撤回等报价本身不应继续使用的情况。
- 客户拒绝状态录入错误时，应通过受权限控制的纠错命令处理，不得借编辑报价绕过审计。本纠错能力不属于本方案第一阶段范围。

## 4. Owner 与边界

### 4.1 唯一 Owner

报价版本关系、可修订条件、字段复制规则、状态重置、审批重置和并发控制由商业域报价服务统一拥有。

建议 owner：

- 核心合同：`apps/api/src/modules/commercial`
- 报价状态规则：报价工作流服务
- 修订版创建：商业域专用 application command/service
- 数据约束：Prisma schema 与数据库唯一约束
- 前端：仅展示服务端提供的版本关系和允许操作，不自行推导版本号或状态转换

### 4.2 非目标

本方案不处理以下内容：

- 不允许 AI 自动修改报价价格或自动创建最终修订版。
- 不自动接受客户提出的新价格。
- 不把报价修订与审批驳回混为同一流程。
- 不为历史数据伪造不存在的修订版。
- 不在第一阶段引入通用的任意报价复制功能。
- 不改变报价计算公式和成本口径。

## 5. 目标流程

```text
R1 草稿
  -> 提交审批
  -> 审批通过
  -> 发送客户
  -> 客户拒绝（R1 保持只读）
  -> 创建修订版 R2
  -> 调整报价内容
  -> 重新提交审批
  -> 审批通过
  -> 重新发送客户
  -> 客户接受 / 客户拒绝
```

状态约束：

| 当前版本状态 | 动作 | 新记录 | 原记录 |
| --- | --- | --- | --- |
| `CUSTOMER_REJECTED` | 创建修订版 | `status=DRAFT`、`approvalStatus=DRAFT` | 保持 `CUSTOMER_REJECTED` |
| `CUSTOMER_REJECTED` | 普通编辑 | 禁止 | 不变 |
| `CUSTOMER_REJECTED` | 再次发送 | 禁止 | 不变 |
| 新修订版 `DRAFT` | 编辑 | 更新当前修订版 | 历史版本不变 |
| 新修订版 `DRAFT` | 提交审批 | `approvalStatus=PENDING_APPROVAL` | 历史版本不变 |

第一阶段仅允许从 `CUSTOMER_REJECTED` 创建修订版。是否允许从 `EXPIRED` 或已发送但未回复的报价创建修订版，应作为独立需求评审，不能顺带扩大状态机。

## 6. 数据模型建议

### 6.1 报价版本族

增加独立的 `QuoteRevisionGroup` 作为报价版本族 owner。每张 `Quote` 必须属于一个版本族，版本族保存稳定的基础编号和客户归属，不承载价格或审批结果。

`QuoteRevisionGroup` 建议字段：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | `String @id` | 版本族主键 |
| `customerId` | `String` | 版本族所属客户 |
| `baseQuoteNo` | `String @unique` | 不含修订号的稳定基础编号 |
| `createdAt` | `DateTime` | 版本族创建时间 |

在现有 `Quote` 上增加以下字段：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `revisionGroupId` | `String` | 指向 `QuoteRevisionGroup` |
| `previousRevisionId` | `String? @unique` | 指向直接来源版本，确保一个版本最多只有一个直接后继版本 |
| `revisionNo` | `Int @default(1)` | 报价族内的递增版本号 |
| `revisionReason` | `String?` | R2 及后续版本必填的修订原因或客户反馈摘要 |
| `revisedById` | `String?` | 创建修订版的操作人 |
| `revisedAt` | `DateTime?` | 创建修订版的时间 |

数据库层使用 `@@unique([revisionGroupId, revisionNo])` 保证版本号在报价族内唯一。`previousRevisionId @unique` 保证版本链不能从同一个来源分叉。版本族关系、直接来源关系和版本序号各自只有一个职责，不使用编号字符串或历史备注代替结构化关系。

### 6.2 报价编号

报价编号由服务端基于版本族基础编号生成。为保持现有手工报价编号和外部引用稳定，R1 保留原报价编号，R2 起追加修订号，例如：

```text
QT-202608-001
QT-202608-001-R02
QT-202608-001-R03
```

编号必须由服务端统一生成。前端不得通过字符串截取、拼接或扫描现有列表计算下一版本号。

现有报价创建仍接收用户填写的 R1 编号；创建修订版时，商业域服务以 `QuoteRevisionGroup.baseQuoteNo` 为唯一基础编号 owner，并统一生成两位修订后缀。前端不得拼接或计算修订编号。

### 6.3 QuoteHistory

建议增加历史动作 `REVISION_CREATED`，用于记录：

- 来源报价 ID、报价编号和版本号。
- 新修订版 ID、报价编号和版本号。
- 创建原因。
- 操作人和时间。
- 新修订版初始完整快照。

版本关系是 `Quote` 的结构化事实，`QuoteHistory` 是审计日志。不能只写历史备注而不建立数据关系。

## 7. 字段复制与重置规则

### 7.1 复制到新修订版

以下字段可作为新草稿的初始值：

- 客户。
- 产品名称和规格。
- MOQ、数量和币种。
- 计价模式。
- 物料明细、损耗率和利润率。
- 加工、税费、运费和优惠相关输入。
- 有效期可带入编辑表单，但保存前应检查是否已经过期。
- 普通报价备注可复制，但应允许操作员修改。

价格结果必须使用当前共享报价计算 owner 重新计算，不能直接信任旧版本结果字段。

### 7.2 必须重置

以下字段不得继承：

- `status` 重置为 `DRAFT`。
- `approvalStatus` 重置为 `DRAFT`。
- 审批意见、提交人、审批人和所有审批时间。
- 发送时间和客户回复结果。
- 邮件发送记录、入站邮件关联和回复判断结果。
- 与旧报价绑定的样品申请关系。
- 旧版客户可见报价文件或导出附件。

旧版报价文件对应客户实际收到的 R1，不能挂到 R2 上继续使用。R2 审批通过后应重新生成或重新上传对应版本文件。

## 8. 服务端命令与事务边界

建议增加专用命令：

```http
POST /quotes/:quoteId/revisions
Content-Type: application/json

{
  "reason": "客户要求降低单价并调整 MOQ"
}
```

服务端在一个事务内完成：

1. 按当前用户数据权限查询来源报价。
2. 校验来源状态必须为 `CUSTOMER_REJECTED`。
3. 校验来源报价是版本链中的最新版本。
4. 校验尚未创建后继修订版。
5. 锁定或以条件更新方式认领当前版本，防止并发创建两个 R2。
6. 计算下一个版本号并生成新报价编号。
7. 按字段白名单构造新报价，重置状态和审批字段。
8. 使用共享报价计算模块重新计算价格结果。
9. 建立版本关系。
10. 写入 `REVISION_CREATED` 历史记录和完整初始快照。
11. 返回新修订版以及版本链摘要。

禁止通过通用 `POST /quotes` 接收 `sourceQuoteId` 来隐式实现修订，也禁止先由前端读取旧报价再拼接创建请求。这两种方式都无法可靠保证复制白名单、权限、并发和审计的一致性。

### 8.1 并发与幂等

以下约束属于阻断项：

- 同一来源报价不能并发创建多个直接后继版本。
- 同一报价族内 `revisionNo` 必须唯一。
- 重复点击或请求重试不得生成多个 R2。
- 若已存在后继版本，接口返回已存在版本的结构化冲突信息，不静默新建分支。

可以使用数据库唯一约束作为最终防线，并配合事务内条件写入；不能只依赖前端按钮禁用。

## 9. 前端交互建议

### 9.1 列表操作

当报价为 `CUSTOMER_REJECTED` 时：

- 隐藏或禁用普通“编辑”按钮。
- 提供“创建修订版”操作。
- 已有后继版本时，操作替换为“查看最新修订版”。
- 保留“查看详情”“查看历史”“导出旧版”等只读能力。

### 9.2 创建修订版对话框

对话框应包含：

- 来源报价编号和版本号，只读。
- 客户拒绝原因或最近一次客户回复摘要，只读展示。
- 修订原因，必填。
- 将被复制与不会被复制的关键内容摘要。
- “创建修订版”确认按钮。

创建成功后直接进入 R2 编辑页或编辑对话框，操作员只调整发生变化的字段。

### 9.3 详情页版本链

报价详情页展示：

- 报价族基础编号。
- 当前版本号。
- 全部版本列表及其状态、金额、审批结果、发送时间和客户结果。
- 当前查看的是历史版本还是最新版本。
- 从当前版本跳转到上一版或下一版的入口。

历史版本必须明确标记为只读，避免用户误以为正在编辑最新报价。

## 10. 权限与审计

- 创建修订版必须复用当前报价创建权限和客户数据范围权限。
- 用户必须同时有权读取来源报价并为该客户创建报价。
- 修订版重新走现有报价审批权限，不继承来源报价的审批授权结果。
- 所有失败返回项目统一结构化错误，至少区分：状态不允许、已有后继版本、编号冲突、权限不足和来源不存在。
- 修订原因、操作人、来源版本和新版本必须进入审计记录。
- 日志不得输出价格成本明细之外的敏感配置、邮件凭据或客户隐私数据。

## 11. 历史数据与迁移策略

### 11.1 既有报价

- 现有报价默认视为各自报价族的 R1。
- 不根据相似编号、相同客户、相同金额或历史备注自动推断版本关系。
- 历史上已被直接修改的客户拒绝报价继续依赖 `QuoteHistory` 回放，不伪造拆分出的 R1/R2。
- 新规则上线后，所有 `CUSTOMER_REJECTED` 报价禁止继续直接编辑。

### 11.2 上线顺序

1. 增加数据字段、关系和唯一约束。
2. 为既有报价初始化版本族和 `revisionNo=1`。
3. 实现商业域修订命令及测试。
4. 收紧服务端可编辑状态。
5. 接入前端创建修订版和版本链展示。
6. 完成导出、邮件和详情页的版本标识。
7. 更新项目类定义参考手册和报价全流程设计真源。

在服务端修订命令可用之前，不应先关闭现有编辑入口，以免形成无法处理客户拒绝报价的业务空窗。

## 12. 验收标准

### 12.1 核心合同测试

- `CUSTOMER_REJECTED` 报价调用普通更新接口必须失败。
- 从非 `CUSTOMER_REJECTED` 状态创建修订版必须失败。
- R1 创建 R2 后，R1 内容、状态、审批结果和发送记录完全不变。
- R2 必须为 `DRAFT + DRAFT`，审批和发送字段为空。
- R2 的计价输入按白名单复制，价格结果由共享计算模块重新计算。
- R2 与 R1 的版本族、前序版本和版本号关系正确。
- 同一 R1 的并发创建请求最多成功一次。
- 已有 R2 后再次请求返回结构化冲突，不创建分叉版本。
- 新修订版必须重新审批，未审批不能发送。
- `QuoteHistory` 能从 R2 追溯来源、原因、操作人和初始快照。

### 12.2 UI 验收

- 客户拒绝报价不能进入普通编辑流程。
- “创建修订版”只在服务端允许时可用。
- 创建对话框包含必填修订原因并正确处理提交中、失败和重复创建状态。
- 创建成功后进入新草稿，原报价仍可只读查看。
- 版本链在桌面和移动端都能明确区分历史版本与最新版本。
- 导出文件、邮件附件和页面标题包含明确版本号。

### 12.3 回归验收

- 草稿编辑、审批提交、审批通过、发送、客户接受、客户拒绝、到期和作废原有主链路通过。
- 报价历史快照仍能正确展示价格计算明细。
- 报价邮件只引用选中的具体版本，不自动切换到最新版本。
- 样品、邮件和导出引用仍指向原来的具体 `quoteId`，不会因创建修订版自动迁移。

## 13. 实施停止条件

出现以下任一情况时，应停止实现并先确认产品或架构决策：

- 报价编号当前由外部系统生成，无法在本系统内确定修订号规则。
- 业务要求一个被拒绝版本能够同时分叉为多套并行方案。
- 外部审批系统以报价 ID 作为不可变合同，且不支持新版本重新审批。
- 客户邮件或附件只保存报价编号而不保存具体报价 ID，无法可靠关联版本。
- 现有下游订单、样品或导出默认引用“最新报价”，而不是具体报价版本。

上述问题会改变版本模型或外部合同，不能通过临时兼容字段、字符串规则或前端判断绕过。

## 14. 最终结论

客户拒绝应终结当前报价版本，而不是终结整个报价机会。后续议价通过“创建修订版”产生新的草稿和新的审批周期：旧版保持不可变，新版继承必要业务输入，版本关系可查询、可审计、可并发约束。

该设计在操作效率、审批正确性、客户争议处理和长期数据治理之间取得一致结果，应作为报价被客户拒绝后的唯一推荐主线。

## 15. 实现记录

本方案由迁移 `apps/api/prisma/migrations/20260806120000_quote_revisions/migration.sql` 落地，当前实现包括：

- `QuoteRevisionGroup` 版本族及 `revisionGroupId + previousRevisionId + revisionNo` 结构化关系。
- `GET /quotes/:id/revisions` 版本链查询。
- `POST /quotes/:id/revisions` 原子创建修订版。
- `CUSTOMER_REJECTED` 普通更新禁用。
- `REVISION_CREATED` 双向历史审计。
- 前端修订原因对话框、版本链和历史版本只读入口。
- 数据库唯一约束与服务端 `QUOTE_REVISION_ALREADY_EXISTS` 冲突响应。
