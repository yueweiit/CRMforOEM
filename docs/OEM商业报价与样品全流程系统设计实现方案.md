## 1. 目标与边界

### 1.1 目标

围绕 OEM 行业真实业务场景，建立一条可落地的商业闭环：

1. 客户询价进入系统后，先完成规则校验、报价草稿、审批、发送和历史留痕。
2. 客户样品申请进入系统后，支持申请登记、审核、打样、寄出、签收、反馈、留样、归还、作废和费用记录。
3. 新建样品时必须同步填写规格、材质、工艺、样品数量、样品用途，以及至少一条费用记录；交付期限为可选字段。
4. 报价与样品不再只是记录型数据，而是可驱动客户阶段推进、后续跟进任务、审批追溯和管理统计的业务对象。
4. 报价邮件支持从已有报价记录生成邮件草稿，并在发送时自动附带报价表格或报价附件。
5. 报价邮件发送成功后，报价业务状态自动同步为 `SENT`，避免销售人员手工重复维护状态。
6. 只有审批通过的报价才能发送给客户，未审批通过的报价只能停留在草稿或审批中状态。

### 1.2 非目标

本轮不把系统扩展成 ERP、WMS 或财务结算系统，以下内容不作为主线：

- 发票、收款、对账、应收应付
- 仓储出入库全流程
- 复杂 BOM/MRP 生产计划
- 订单履约的物流跟单系统

这些能力可在后续作为外部系统对接，而不是抢占 CRM 的核心边界。

## 3. OEM 业务主流程

### 3.1 客户询价规则

客户询价不是“直接建一条报价”这么简单，建议先做规则校验：

1. 校验客户是否可见、是否在业务范围内。
2. 校验客户状态是否允许进入报价阶段。
3. 校验客户是否命中黑名单、禁发、重复客户或无效客户。
4. 校验是否已有未完成报价，避免重复报价冲突。
5. 校验客户是否已有有效联系人、基础币种、国家、语言等信息。
6. 校验是否存在样品、历史报价、审批意见等上下文。

### 3.2 报价流程

推荐主流程：

1. 新建报价草稿
2. 录入报价明细
3. 计算价格公式
4. 提交审批
5. 审批通过
6. 导出报价单
7. 发送给客户
8. 记录客户反馈
9. 报价作废或过期关闭

建议将“导出报价单”和“发送给客户”进一步细化为：

1. 基于当前报价生成邮件草稿
2. 草稿自动关联报价表格或报价附件
3. 系统先校验该报价是否已审批通过，未通过则禁止进入发送流程
4. 销售人员确认收件人、正文和附件
5. 发送成功后，将报价业务状态同步为 `SENT`
6. 同步记录邮件线程、附件和报价发送历史

### 3.3 样品流程

推荐主流程：

1. 新增样品申请
2. 审核样品申请
3. 打样/备样
4. 寄出
5. 客户签收
6. 留样登记
7. 归还/销毁/转入后续报价
8. 记录费用与反馈
9. 作废关闭

本轮应以更收敛的主线约束样品流程：

- 样品申请登记后，默认状态为 `待审核`
- 审核通过后进入 `打样中`
- 审核通过 / 驳回时都应支持填写可空的审批备注，并在样品详情与历史中保留
- 只有在填写 `物流商` 和 `运单号` 后，才能将状态变更为 `已寄出`
- 客户签收后状态变更为 `已签收`
- 报价与样品记录的“更多”菜单只展示当前状态允许执行的下一步动作；不可执行动作不展示，所有状态变更必须先进入确认或信息填写弹窗，再由用户确认提交
- 无法继续推进或申请取消时，可进入 `作废`
- 样品必须始终关联 `客户`，并支持关联 `后续报价订单`
- 样品费用需按单据持续记录，至少覆盖打样费、快递费、包装费和其他费用

#### 3.3.1 报价与样品更多菜单

“历史记录”在所有状态下始终显示。下表列出“更多”菜单中随状态动态出现的操作；表中未列出的操作均不展示。

**报价记录**

| 当前状态 | 更多菜单显示的状态操作 |
| --- | --- |
| 新建 / 审批驳回 | 提交审批 |
| 待审批 | 审批通过、审批驳回 |
| 审批通过 | 发送报价 |
| 已发送 | 客户接受、客户拒绝 |
| 客户接受 / 客户拒绝 / 到期失效 / 作废关闭 | 不显示状态操作 |

**样品记录**

| 当前状态 | 更多菜单显示的状态操作 |
| --- | --- |
| 待申请 / 审批驳回 | 发起审核 |
| 待审核 | 审核通过、审核驳回 |
| 打样中 | 标记已寄出 |
| 已寄出 | 确认签收 |
| 已签收 | 记录归还、记录留样 |
| 已反馈 | 记录归还、记录留样、关闭样品 |
| 已归还 | 记录留样、关闭样品 |

所有上述操作必须先进入确认或信息填写弹窗。特别是“标记已寄出”必须填写物流商、运单号和发货日期；“记录归还”与“记录留样”保留归还或留样登记字段。

| 样品没有留样/归还流程 | 未实现 | P0 | 中 | 样品全流程 |
| 样品状态不含作废/归还 | 未实现 | 低 | 低 | 状态完整性 |
| 样品与后续报价订单关联弱 | 未实现 | P1 | 中 | 转化闭环 |
| 商业操作无统一事件历史 | 未实现 | P0 | 中 | 审计、分析、复盘 |
| 报价附件只预留 `fileAssetId`，未形成上传/预览链路 | 部分存在 | P1 | 中 | 文档管理 |
| 报价和样品没有统一的 follow-up 触发规则 | 未实现 | P1 | 中 | 自动跟进 |

### 4.1 当前已知的实现型 BUG

1. 报价新建接口把状态直接设为 `SENT`，这会绕过草稿和审批。
2. 样品只做了基础状态枚举，缺少 `VOIDED`、`RETURNED`、`STORED` 这类 OEM 常见状态。
3. 报价和样品的更新、删除没有历史记录，发生争议时无法回放。
4. 目前商业模块已具备基础价格公式，但尚未扩展到多币种换算、毛利率、税率拆分和运费分摊等更细的 OEM 定价模型。
5. 当前样品只保存物流和反馈信息，不足以表达“留样后转报价”这一常见业务动作。

## 5. 推荐系统设计

### 5.1 模块边界

建议把商业域继续收敛在 `commercial` 作为唯一 owner：

- `customers` 只负责客户主数据
- `commercial` 负责报价、样品、商业事件、审批、导出、公式
- `follow-ups` 只消费商业域事件，生成跟进任务
- `settings` 只配置权限、审批规则、报价模板、费用策略

### 5.2 报价域设计

建议报价对象拆成四层：

1. `Quote`：报价单头，承载客户、报价编号、币种、有效期、状态、审批结果
2. `QuoteItem`：报价行项目，承载物料、加工费、数量、单价、折扣
3. `QuoteCostBreakdown`：成本拆分，承载物料价、加工费、税费、运费、汇率、毛利
4. `QuoteHistory`：历史版本与操作日志，承载每次修改、审批、导出、作废原因
5. `QuoteEmail`：报价邮件草稿与发送记录，承载邮件主题、正文、收件人、附件、发送结果与报价绑定关系

### 5.3 样品域设计

建议样品对象拆成五层：

1. `SampleRequest`：样品申请单头
2. `SampleItem`：样品明细，支持多个样品项
3. `SampleFlowEvent`：状态流转事件
4. `SampleFee`：费用记录，包含打样费、快递费、包装费、返还费用等，且新建样品时必须至少写入一条初始费用
5. `SampleReturnRecord`：留样/归还记录，支持归还日期、归还状态、去向说明

### 5.4 状态设计建议

#### 报价状态

推荐将报价状态从单一业务状态扩展为“审批态 + 业务态”组合管理：

- 审批态：`DRAFT`、`PENDING_APPROVAL`、`APPROVED`、`REJECTED`
- 业务态：`DRAFT`、`SENT`、`ACCEPTED`、`CUSTOMER_REJECTED`、`EXPIRED`、`VOIDED`

这样可以避免“刚建单就是已发送”的语义错误。
其中 `CUSTOMER_REJECTED` 代表客户拒绝，审批驳回则由审批态 `REJECTED` 表达。

#### 样品状态

推荐样品状态至少覆盖：

- `REQUESTED`
- `APPROVING`
- `PREPARING`
- `SHIPPED`
- `DELIVERED`
- `FEEDBACK_RECEIVED`
- `RETURNED`
- `STORED`
- `VOIDED`
- `CLOSED`

### 5.4.1 报价状态流转规则

报价建议把“审批态”和“业务态”分开管理，避免审批结果和客户结果混在同一字段里。

审批态只表达内部审核结果，业务态只表达对客户可见的报价生命周期。

| 当前状态 | 允许动作 | 目标状态 | 说明 |
| --- | --- | --- | --- |
| `DRAFT` | 新建 / 编辑 | `DRAFT` | 报价草稿可反复修改，价格公式在每次保存时重算。 |
| `DRAFT` | 提交审批 | `PENDING_APPROVAL` | 进入审批流后，审批态变为待审批。 |
| `PENDING_APPROVAL` | 审批通过 | `APPROVED` | 通过后才能进入发送链路。 |
| `PENDING_APPROVAL` | 审批驳回 | `REJECTED` | 允许返回草稿修改后重新提交。 |
| `APPROVED` | 发送报价 | `SENT` | 只有审批通过的报价才可发送。 |
| `SENT` | 客户接受 | `ACCEPTED` | 客户接受后进入终态。 |
| `SENT` | 客户拒绝 | `CUSTOMER_REJECTED` | 客户拒绝后进入终态，可作为后续跟进依据。 |
| `CUSTOMER_REJECTED` | 创建修订版 | 新建一条 `DRAFT` 报价 | 原版本保持只读，新版本重置审批并重新进入审批发送链路。 |
| `SENT` | 到期失效 | `EXPIRED` | 超过有效期后关闭。 |
| 任意可编辑状态 | 作废关闭 | `VOIDED` | 作废后不再继续流转。 |

补充约束：

- 报价普通编辑只更新业务字段，不应通过通用保存接口夹带状态变更。
- `VOIDED` 是终态，作废后不再允许继续编辑或发送。
- `CUSTOMER_REJECTED` 是单个报价版本的终态，禁止普通编辑；重新议价必须通过专用修订命令创建新版本。
- 报价版本关系由 `QuoteRevisionGroup`、`previousRevisionId` 和 `revisionNo` 共同表达，不依赖备注或编号字符串推断。
- `SENT` 是客户动作入口，只有在该状态下才允许客户接受、客户拒绝或到期失效。
- `REJECTED` 同时存在于审批态和业务态语义中时，必须依赖上下文区分，避免把“审批驳回”和“客户拒绝”混为一谈。

### 5.4.2 样品状态流转规则

样品建议使用单条状态机覆盖申请、审核、制样、寄出、签收、反馈、留样、归还和关闭。

| 当前状态 | 允许动作 | 目标状态 | 说明 |
| --- | --- | --- | --- |
| `REQUESTED` | 提交审核 / 驳回取消 | `APPROVING` / `VOIDED` | 样品申请的起点。 |
| `APPROVING` | 回退修改 / 进入制样 / 作废 | `REQUESTED` / `PREPARING` / `VOIDED` | 审核过程中允许退回补充信息。 |
| `PREPARING` | 寄出 / 作废 | `SHIPPED` / `VOIDED` | 制样完成后才能进入物流节点。 |
| `SHIPPED` | 签收 / 作废 | `DELIVERED` / `VOIDED` | 寄出后必须记录物流信息。 |
| `DELIVERED` | 反馈 / 留样 / 归还 / 关闭 / 作废 | `FEEDBACK_RECEIVED` / `RETURNED` / `STORED` / `CLOSED` / `VOIDED` | 签收后进入结果回收阶段。 |
| `FEEDBACK_RECEIVED` | 归还 / 留样 / 关闭 / 作废 | `RETURNED` / `STORED` / `CLOSED` / `VOIDED` | 已收到反馈后可继续处理样品去向。 |
| `RETURNED` | 留样 / 关闭 / 作废 | `STORED` / `CLOSED` / `VOIDED` | 已归还后可转为留样或关闭。 |
| `STORED` | 关闭 / 作废 | `CLOSED` / `VOIDED` | 留样后可关闭。 |
| `CLOSED` | 无 | 无 | 终态。 |
| `VOIDED` | 无 | 无 | 终态。 |

补充约束：

- 只有在填写物流商和运单号后，才允许从制样阶段进入 `SHIPPED`。
- `RETURNED` 和 `STORED` 只能从已寄出、已签收或已反馈的样品继续流转，不允许从草稿态直接跳转。
- 状态变化要同步写入时间戳字段，例如 `approvedAt`、`shippedAt`、`deliveredAt`、`returnedAt`、`storedAt`、`voidedAt`、`closedAt`。
- 样品费用、反馈和附件可以随着状态推进持续补充，但不能破坏状态机的单向约束。

### 5.5 价格公式设计

报价计算建议固定为可解释公式，不要把核心金额完全交给人工输入。

当前仓库已落地的基础公式如下，适合作为 OEM CRM 的首版报价口径：

```text
总价 = 物料价 + 加工费 + 税费 + 运费 - 优惠金额
单价 = 总价 / 数量
```

建议字段：

- `materialCost`
- `processingCost`
- `taxCost`
- `shippingCost`
- `discountAmount`
- `subtotal`
- `amount`
- `unitPrice`

实现约束：

- 物料价、加工费、税费、运费、优惠金额统一按金额字段保存，落库前保留两位小数。
- 数量必须大于等于 MOQ，低于 MOQ 时拒绝保存。
- 计算逻辑必须在后端与前端预览共用同一份公式定义，避免口径分叉。
- 后续如果要加入汇率、毛利率、税率或运费分摊，应先扩展合同，再改公式，不要在 UI 里临时拼接。

### 5.6 审批设计

报价审批建议使用“单据审批 + 审批历史”：

- 提交审批时锁定报价快照
- 审批通过后允许导出、发送
- 审批拒绝后可回到草稿修改
- 任何审批意见都必须写入历史

审批人建议来源于：

- 角色权限
- 金额阈值
- 客户等级
- 产品线
- 特殊折扣规则

### 5.7 历史与审计设计

建议所有商业动作统一写入一张事件表，或至少统一写入同一套历史结构：

- 新建
- 修改
- 作废
- 审批提交
- 审批通过
- 审批拒绝
- 导出
- 寄出
- 签收
- 留样
- 归还
- 费用变更

这张历史表的价值不是“多存一点日志”，而是让销售、主管、财务、客服都能还原事实。

## 8. 里程碑建议

### M1：报价主流程纠偏

交付目标：

- 报价单先草稿后审批
- 报价状态和审批状态分离
- 报价历史可追踪
- 报价邮件可基于已有报价生成草稿，并在发送时附带报价表格
- 报价邮件发送成功后自动将报价业务状态同步为 `SENT`
- 仅审批通过的报价允许进入发送流程

验收标准：

- 新建报价不会直接进入已发送
- 任意报价修改都有历史记录
- 审批通过后才允许导出或发送
- 发送报价邮件后，系统内报价状态会自动变为 `SENT`
- 邮件线程可查询到该报价的附件与发送记录
- 未审批通过的报价在发送前会被拦截

### M2：价格公式与导出

交付目标：

- 物料价、加工费、税费、运费公式化
- 支持 PDF / Excel 导出
- 支持邮件上传附件，并复用报价导出结果作为邮件附件

验收标准：

- 同一输入得到同一结果
- 导出文件可用于对外报价
- 导出快照和系统数据一致
- 邮件发送时可正确附带报价表格或报价附件
- 未审批通过的报价无法生成可发送邮件

### M3：样品全流程

交付目标：

- 样品申请、打样、寄出、签收、反馈、留样、归还、作废完整闭环

验收标准：

- 每次状态流转都有事件记录
- 可查询样品费用与归属客户
- 样品能正确关联后续报价或成交线索

### M4：联动和运营

交付目标：

- 商业节点自动生成跟进任务
- 商业数据进入管理看板

验收标准：

- 报价后、样品后能自动产生跟进提醒
- 管理看板能看到报价转化、样品转化与停留时长

## 9. 建议的实施顺序

1. 先修报价状态与审批语义，避免现有 `SENT` 逻辑继续污染业务。
2. 再补历史记录、价格公式和报价邮件草稿，让报价单具备可追溯、可计算和可发送能力。
3. 同步补齐邮件附件上传与报价邮件发送后状态同步，确保邮件链路与报价状态一致。
4. 随后补齐样品状态、费用、留样和归还。
5. 最后把商业事件接入 follow-up 和报表。

- 跟进任务页前后端路由不一致
- 审计日志有查询但写入不完整
- 文件上传链路不完整
- 邮件附件上传与报价邮件发送链路未形成闭环
- 报价邮件发送后未统一回写报价状态

这些问题会影响整体 CRM 体验，但不改变本方案的商业域主线。

## 11. 结论

当前系统已经有“报价/样品基础记录”的底座，但 OEM 真实业务需要的是“可审批、可追溯、可计算、可导出、可联动”的商业流程。

因此，本方案建议的主线不是重写，而是：

1. 保留现有客户详情页里的报价/样品入口
2. 在 `commercial` 域内补齐审批、历史、公式、导出、邮件附件、报价邮件草稿、状态同步、费用、留样、归还
3. 用统一事件和权限把商业动作接到客户阶段、邮件线程和跟进任务上

这样既能复用当前已有能力，也能把 OEM 场景真正闭环起来。
