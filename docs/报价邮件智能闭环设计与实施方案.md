# 报价邮件智能闭环设计与实施方案

版本：v1.2
日期：2026-08-11
状态：已实现并完成本地验收，真实邮箱联调待部署环境执行
适用范围：报价邮件生成、邮件草稿手动附件、历史报价参考、邮件发送联动、客户回信判断、人工确认

## 1. 目标与非目标

### 1.1 目标

建立以下可审计闭环：

```text
已审批报价
  -> 选择报价并生成邮件草稿
  -> 可选读取有限的历史报价参考
  -> 人工审核邮件
  -> SMTP 发送成功
  -> 报价自动变为 SENT
  -> IMAP 收到客户回复并关联原报价
  -> AI 生成结构化回复建议
  -> 操作员确认
  -> 报价变为 ACCEPTED 或 CUSTOMER_REJECTED
```

### 1.2 非目标

- AI 不拥有报价价格，不直接创建最终价格，不修改报价计算公式。
- AI 不自动发送邮件。
- AI 不直接把报价改为客户接受或客户拒绝。
- 不把全部历史报价无界发送给模型。
- 不用主题、发件人或提示词猜测代替报价与邮件的结构化关联。
- 不把现有内部核价 XLSX 直接作为客户附件；内部成本、损耗率和利润率不得对外发送。
- 不自动生成、选择或附带报价表；附件只来自操作员在当前邮件草稿中的主动上传。

## 2. Owner 与边界

### 2.1 商业域 `commercial`

唯一拥有以下语义：

- 报价价格、币种、MOQ、数量、有效期和审批结果。
- 报价生命周期及允许的状态转换。
- 报价历史记录。
- 历史报价参考的筛选和脱敏投影。

### 2.2 邮件域 `emails`

只负责：

- 生成和保存邮件草稿。
- SMTP 发送与发送结果归档。
- IMAP 收件、MIME 正文解析和线程关联。
- 基于真实入站邮件生成待人工确认的报价回复建议。

邮件域只能调用商业域提供的报价状态命令，不能直接私造报价状态机。

通用 `PATCH /quotes/:id` 只允许修改报价内容，不允许直接写入生命周期状态；发送、接受、客户拒绝、过期和作废必须走专用命令。

### 2.3 前端

前端只展示后端提供的报价、参考记录、回复建议和允许操作。前端不得自行推导价格结论、客户意图或状态转换权限。

## 3. 核心合同

### 3.1 报价邮件生成

当 `purpose=QUOTATION` 时：

- `quoteId` 必填。
- 报价必须属于当前客户和当前组织，且用户有权访问。
- 报价审批状态必须为 `APPROVED`。
- 报价业务状态只允许 `DRAFT` 或 `SENT`；`SENT` 用于重新发送或跟进现有报价。
- `useHistoricalQuoteReferences=true` 时，服务端最多选择 5 条参考记录。

历史记录筛选顺序：

1. 同组织且当前用户具备历史价格参考权限。
2. 审批状态为 `APPROVED`。
3. 业务状态为 `ACCEPTED` 或 `SENT`，优先 `ACCEPTED`。
4. 币种一致。
5. 产品名、规格和数量区间相近。
6. 按匹配分和更新时间排序，最多 5 条。

AI 输入只包含必要投影：报价编号、产品、规格、MOQ、数量、币种、单价、总价、有效期、状态和日期；不向模型暴露其他客户身份或内部成本拆分。

选中报价是邮件价格的唯一真源。历史记录用于解释与参考，不得覆盖选中报价的价格。

### 3.2 发送联动

报价邮件草稿与外发消息都必须保存 `quoteId`。发送前再次检查：

- 草稿已审核。
- 报价仍属于同一客户。
- 报价仍已审批。
- 报价更新时间与草稿保存的报价快照一致；不一致则要求重新生成或审核。

SMTP 失败不改变报价状态。SMTP 成功后，在一个数据库事务中完成邮件归档、草稿状态、报价状态和报价历史。

由于 SMTP 与数据库无法组成同一事务，发送过程必须有幂等 dispatch。若 SMTP 已确认但数据库收尾失败，dispatch 进入待对账状态，禁止自动重复发信。

### 3.3 邮件草稿手动附件

邮件附件采用以下唯一链路：

```text
操作员选择本地文件
  -> FileAsset / S3
  -> EmailDraftAttachment
  -> 人工审核
  -> SMTP attachments
  -> EmailAttachment 发送快照
```

- 操作员只能为有权访问且尚未发送的草稿增删附件；服务端同时校验组织边界和客户数据范围。
- 每封草稿最多 5 个附件，单个文件最多 10 MiB，原始文件总量最多 15 MiB，并限制允许的文件扩展名。
- 增加或删除附件后，草稿统一回到 `PENDING_REVIEW`，并清空原审核人、审核时间和审核意见。
- 发送前由服务端按草稿附件顺序从文件资产读取有界内容，前端不得提交本地路径、远程 URL 或 SMTP 附件参数。
- SMTP 成功归档时，将文件资产 ID、文件名、MIME 和大小写入 `EmailAttachment`，作为该次外发消息的附件快照。
- 本能力适用于普通邮件和报价邮件，但两者都不会自动生成或附带报价表。

### 3.4 客户回信判断

IMAP 必须有界读取 MIME 源：

- 单封原始邮件最大 1 MiB。
- 用成熟 MIME 解析器提取 `text/plain` 和 `text/html`。
- 解析时限制纯文本和 HTML 长度；当前只持久化受限纯文本，未经清洗的 HTML 不进入前端展示。
- 分类前移除引用历史、签名和自动回复噪声。
- 附件继续走既有文件资产链路，不把附件内容直接发送给分类模型。

报价关联优先级：

1. `In-Reply-To` / `References` 命中带 `quoteId` 的外发消息。
2. 同组织、同联系人、同线程的唯一已发送报价。
3. 无法唯一确定时不创建可操作建议。

分类输出固定为：

- `ACCEPT`
- `REJECT`
- `NEGOTIATE`
- `QUESTION`
- `UNCERTAIN`

AI 输出必须是结构化 JSON，并保存意图、置信度、证据片段、理由、模型和提示词版本。解析失败、模型不可用或证据不足时一律降级为 `UNCERTAIN`。

只有明确的 `ACCEPT` 或 `REJECT` 创建待确认建议并主动提示操作员。报价状态在操作员确认之前保持 `SENT`。

## 4. 数据模型

### 4.1 现有实体扩展

- `EmailDraft.quoteId`：草稿关联报价。
- `EmailDraft.quoteSnapshot`：生成时的报价外发快照。
- `EmailDraft.historicalQuoteIds`：实际使用的历史参考 ID，最多 5 个。
- `EmailMessage.quoteId`：外发消息及其回复链关联报价。
- `Quote.sentAt`：首次真实发送成功时间。

### 4.2 `QuoteEmailDispatch`

记录 SMTP 外部副作用和数据库收尾：

- `quoteId`
- `emailDraftId`
- `emailMessageId`
- `idempotencyKey`
- `status`: `PENDING | SENDING | SENT | FAILED | ACKED_PENDING_RECONCILE`
- `providerMessageId`
- `errorMessage`
- `attemptedAt`
- `sentAt`
- `createdAt` / `updatedAt`

`emailMessageId` 在发送前预建，以便生成确定性 Message-ID 和完成幂等认领。

### 4.3 `EmailDraftAttachment`

- `emailDraftId`
- `fileAssetId`
- `filename`
- `mimeType`
- `sizeBytes`
- `sortOrder`
- `createdById`
- `createdAt`

`EmailAttachment.fileAssetId` 建立真实外键；草稿附件在发送成功归档时复制为外发消息附件快照。

### 4.4 `QuoteReplyAssessment`

- `organizationId`
- `quoteId`
- `inboundEmailMessageId`，唯一
- `aiGenerationRunId`
- `intent`
- `confidence`
- `evidence`
- `reason`
- `status`: `PENDING | CONFIRMED | DISMISSED | STALE`
- `reviewedById` / `reviewedAt`
- `createdAt` / `updatedAt`

### 4.5 客户版报价附件

现有报价导出属于内部核价文件，包含成本、物料单价、损耗率和利润率。本轮手动附件能力不生成报价表。后续若要自动生成客户版报价附件，必须另行建立独立的客户版 projection，仅允许包含报价编号、产品、规格、MOQ、数量、币种、单价、总价、有效期和明确的对外条款，并单独完成产品与安全评审。

## 5. API

- `GET /quotes/:id/reference-candidates`：返回有界、脱敏的历史报价参考。
- `POST /customers/:customerId/email-drafts/generate`：增加 `quoteId`、`useHistoricalQuoteReferences`。
- `POST /email-drafts/:id/attachments`：上传并关联一个草稿附件，成功后使草稿重新待审。
- `DELETE /email-drafts/:id/attachments/:attachmentId`：删除一个草稿附件，成功后使草稿重新待审。
- `GET /quote-reply-assessments?customerId=:customerId&status=PENDING`：读取客户待处理建议。
- `POST /quote-reply-assessments/:id/confirm`：人工确认并执行报价状态转换。
- `POST /quote-reply-assessments/:id/dismiss`：忽略建议，不修改报价。

所有写接口必须校验实时会话、组织边界、数据范围和专用权限。

## 6. 权限与审计

新增权限：

- `quotes.read`
- `quotes.write`
- `quotes.approve`
- `quotes.send`
- `quotes.reference.read`
- `quotes.resolve_reply`

生成报价邮件还要求 `emails.generate`；实际发送还要求 `emails.send`。人工确认必须写入报价历史和回复建议审核字段。

## 7. UI 交互

选择“报价邮件”后显示：

- 已审批报价选择器。
- “参考历史报价记录”复选框。
- 当前报价摘要。
- 实际引用的历史报价列表及匹配依据。

收到高置信度报价回信后：

- 显示持久提醒并跳转客户邮件页。
- 邮件页显示客户原文证据、AI 建议和置信度。
- 操作员可确认、忽略，或打开邮件线程继续判断。
- `NEGOTIATE`、`QUESTION`、`UNCERTAIN` 只显示阅读提示，不提供一键改变报价状态。

邮件草稿展开后显示附件区：未发送草稿可多选上传、打开和删除附件；已发送草稿只读展示附件。附件区展示数量、文件名、大小和限制说明，上传或删除后的重新审核状态由后端返回结果驱动。

邮件历史采用页面单滚动：草稿列表、单封邮件详情和正文编辑器均不得创建独立纵向滚动容器；同一时刻只展开一封草稿，正文高度随内容和可用宽度自动调整，筛选栏在页面滚动时吸顶。桌面端和移动端都不得因此产生页面横向溢出。

## 8. 验收门禁

### 8.1 后端

- 历史参考不能跨组织泄露，最多 5 条。
- 未审批报价不能生成报价邮件。
- AI 输入中的选中报价数值与数据库快照完全一致。
- SMTP 失败不改变报价状态。
- 重复发送请求不会发送两封邮件。
- SMTP 已成功而数据库收尾失败时进入待对账，不自动重发。
- 附件上传校验组织/数据范围、类型、单文件大小、总大小和数量上限。
- 附件增删后草稿必须重新待审，已发送草稿拒绝修改附件。
- 普通邮件和报价邮件发送时均向 SMTP 传入附件，并归档 `EmailAttachment` 快照。
- 文件被草稿或历史消息引用时，通用文件删除接口拒绝删除。
- IMAP 超大邮件被有界拒绝或截断。
- 同邮箱跨组织不能串线。
- 明确接受、明确拒绝、还价、条件接受、询问、含糊、自动回复均有 fixture。
- 人工确认前报价保持 `SENT`。
- 重复确认和并发确认只能成功一次。

### 8.2 前端

- 报价邮件表单的加载态、空态、错误态和权限态可见。
- 发送失败后报价仍显示原状态。
- 回复建议在桌面和移动视口不重叠、不溢出。
- 确认弹窗明确展示将要改变的报价和目标状态。

### 8.3 命令

```bash
npm run db:generate
npx prisma validate --schema apps/api/prisma/schema.prisma
npm run lint
npm run build
```

针对新增服务补充可直接执行的规格测试，并在最终验收中记录实际命令与结果。

## 9. 实施结果

以下阶段已完成：

1. 统一客户拒绝状态为 `CUSTOMER_REJECTED`，收紧报价状态命令与权限。
2. 增加 Prisma 合同、结构迁移、现有组织权限迁移和报价邮件关联。
3. 增加历史报价参考服务、脱敏投影和报价邮件上下文。
4. 增加确定性 Message-ID、幂等 dispatch、SMTP 成功后的报价 `SENT` 联动和待对账状态。
5. 增加 1 MiB 上限 MIME 读取、租户安全匹配、AI 回复分类、建议查询和确认/忽略接口。
6. 增加前端报价选择、历史参考开关、报价页预选跳转、回复建议人工确认和持久 SSE 提醒。
7. 完成 Prisma 校验、迁移部署、类型门禁、聚焦规格测试、生产构建和桌面/移动浏览器验收。
